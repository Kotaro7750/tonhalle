# ドキュメントのスコープ
本ドキュメントは以下をスコープとする。

- 音源データに関連する各ストレージの責務と共通方針
- 音源データストレージの識別・保存・取得・配信・エクスポート要件
- インポート元ストレージの列挙・取得要件

音源データのフォーマットと取り込み・検証については[music_data.md](./music_data.md)で定義する。

# 共通方針
音源データストレージとインポート元ストレージは、それぞれの責務に応じた要件を満たす限り、具体的な保存基盤や内部表現を選択できる。
両者の保存基盤は独立して選択でき、音源の取得は保存基盤固有の表現に依存せず、元の音源ファイルのバイト列として行える必要がある。

# 音源データストレージ
## 責務と基本要件
音源データストレージは、識別子を付与された音源を保持し、バックエンドからの操作とコンテンツ配信を支える。
音源データストレージは以下の要件を満たす必要があり、逆にこれらの要件を満たす限り具体的な実装は選択可能である。

- ポータビリティを第一に考え、下記に示すようにエクスポートできること
- [domain.md](./domain.md)で定義する識別子を利用して常に同じ音源データのエンティティを一意に識別・データバイナリを取得できること
  - これはバイナリとして同じ音源データなら同じ識別子を持つことを意味するものではない
- コンテンツ配信エンドポイント経由でのコンテンツファイルHTTP配信時に、クライアント側での特殊な復元処理なしで、適切なContent-Typeを持つコンテンツファイルのバイト列を取得できること
  - Rangeリクエストやキャッシュの制御など、静的ファイル配信において一般的に必要とされる機能を可能な限り実装していることが望ましい
- バックエンドからのアクセスにおいて、下記に示すような操作が行えること

要件を満たす限り、実際の内部表現において圧縮・暗号化・分割などを行うことは許容する。
また、音源データストレージは単体のコンポーネントである必要はなく、あくまでも外部とのインタフェースが要件を満たす限り、内部的に複数のコンポーネントから構成されていても良い。

## エクスポート要件
音源データストレージは、音源データを通常のツールで扱える以下のようなディレクトリパス中のファイル名の標準ファイルとしてエクスポートできる必要がある。

```
アーティスト名/リリース名/トラックタイトル.{音源データファイルの拡張子(小文字)}
```

この際、パスやファイル名中の表示名はその際のメタデータから取得する。
もし音源データのライフサイクル中にメタデータが更新されていた場合は、初期値ではなくエクスポート時の最新のメタデータを用いる。

また、音源データストレージ単体としてエクスポートできる必要はなく、エクスポート用のコマンドによる間接的なエクスポートが行えれば良い。

メタデータ欠落・エクスポート時の衝突・文字コードの取り扱いなど詳細なエクスポートの挙動については別途検討するものとする。

## バックエンドからの操作要件
音源データストレージは、バックエンドにおける処理を念頭に、以下の操作を行える必要がある。

- Releaseの識別子と、それに所属する全音源データの列挙
- 音源データに対するCRUD操作
- リリース単位での音源データ保存
- 音源データに対するバージョン情報の取得
  - ここでいうバージョン情報は検索用DBの更新判定に利用できるものであり、必ずしもバージョンそのものである必要はなく例えばタイムスタンプ等でも良い

# インポート元ストレージ
## 責務と基本要件
インポート元ストレージは、インポート対象の音源を提供する読み込み専用のストレージとする。

## 列挙・取得要件
インポート元ストレージは、以下の操作を行える必要がある。

- 対象範囲に含まれる複数のリリース候補と、それぞれに所属する音源の列挙
- 列挙した音源のバイト列の取得

リリース候補と音源の対応づけ、対象範囲の指定方法、列挙順は各実装の責務とする。
リリース候補はインポート対象のまとまりであり、その中に含まれる対象は、本アプリケーションのドメインモデルでの識別子を持つことは要求しない。
また、識別子は音源データ中のメタデータから生成するため、たとえ識別子を持っていたとしてもそれが利用される保証はない。
