# ドキュメントのスコープ
本ドキュメントは以下をスコープとする。

- バックエンドコードの読みやすさと保守性を維持するためのコーディング規約
- モジュールの構造化、コメント、テストに関する指針

なお、OpenAPIによる自動生成コードについてはこのコーディング規約の対象外とし、ツールによる生成成果物をそのまま利用する。

# 原則
コーディングを行う上での原則として、コードは読みやすさと保守性を第一に考え、以下の点に注意する。

- モジュールやソースファイルは適切に構造化を行う
- 適切な粒度でコメントを付与する
- テストによってロジックの正しさに自信を持てるような状態を維持する
- コードの規模は不必要に大きくしない

# 構造化
前提として、[software_architecture.md](./software_architecture.md)に規定する層の責務と依存関係を守った上で、その範囲で責務や注目領域に応じてモジュールやファイルは適切に分割することとする。
これによって、コードの理解を容易にし、変更時の影響範囲を最小化することができる。

構造化を行う上では、以下の指針に従う。

- 1つのモジュール・ソースファイルが、複数の注目領域を扱っている状態で規模が肥大化している場合において、分割を検討する
  - 目安として、行数が2~500行程度を超える場合には分割による構造化を検討する
  - 1つの注目領域に閉じているモジュール・ソースファイルは、行数だけを理由に分割してはならない
- 単体テストは基本的に実装モジュールと同じファイルに配置し、テストの規模が増えた場合は別ファイルへの切り出しを検討する

また、関数やメソッド内の処理の構造化については、以下の指針に従う。

- 変数の宣言・処理のまとまりなど、コードは一定の粒度のまとまりを意識して改行を行う

# コメント
原則として、公開範囲によらずシンボルには適切にドキュメンテーションコメントを付与することとし、その際には以下の指針に従う。

- そのシンボルの役割を説明しつつ、シンプルさを意識して簡潔に記載する
  - 基本的には1文で完結することを想定する
- 役割の説明に加えて説明が必要な場合には、1行空けてから特記事項のコメントを追加する
  - 呼び出し側が想定しにくい前提条件や副作用がある場合に記載する
    - 型やシンボル名で誤解を避けられる場合は、コメントによる補足よりも型や命名の改善を優先する
  - 引数・フィールド・返り値を言い換えるだけの説明は、冗長で変更に追従しにくいため記載してはならない
- テストケース関数は、後述のように関数名がそのままテストの機体挙動を示すためシンボルのコメントは不要である

また、実装中のコメントについては、基本的には記載しないものの、必要に応じて以下の指針に従ったコメントを付与する。

- 複雑な処理や一目では理解しにくい実装に対してのみ付与する
  - コメントの要否は読むことで認知負荷が軽減されるかを基準に判断する
  - 付与する状況の例
    - 複雑な処理に対して冒頭の箇条書きで処理の流れを説明し、実装部分にステップ毎の見出しコメントを付与する
    - 複雑なワンライナー・アルゴリズムに対して、処理の概要を説明するコメントを付与する
    - 一見すると意図を汲み取れない実装・処理に対して、意図を説明するコメントを付与する

さらに、上記の2種類のコメントは共通して以下の指針に従う。

- コメントは英語で記載する
- 1行につき1文で記載し、長いからといって1文を複数行に分割してはならない
  - リンター・フォーマッターによる自動整形を優先する

# テスト
テストは、単体テストと統合テストの両方を行い、以下の指針に従う。

- テストは数や規模が多いほど良いわけではなく、価値の高いテストのみを残す必要がある
  - 価値の高いテストとは、バグの再発防止やリファクタリングの安全性を担保するために有効なテストである
  - 価値の低いテストとは、実装の詳細を確かめるだけのテストや、同じ挙動を確認する複数のテストが存在する場合、対象にバグの余地が少ない場合などである
- 単体テストは、単独の振る舞いや責務を対象とする
  - ただし複数の対象が関わる方がより自然な場合、複数の対象を含めることは許容する
- 統合テストは、アプリケーションの利用者側から見た挙動の正しさを対象とする
- テストは実装の詳細を確かめるのではなく、対象が満たすべき挙動や契約を満たしているかを確かめる
- 外部クレートやサービス自体の挙動をテストするのではなく、あくまでもこのクレートのコードをテストする
- テスト名称は、そのテストの対象シンボルと期待する挙動を元に、`テスト対象_期待する挙動`というアンダースコア区切りの形式で命名する
